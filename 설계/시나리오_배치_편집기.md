# 시나리오 편집툴

Unity 메뉴 **DarkSaver → 시나리오 편집툴**에서 연다. 현재 ScenarioCatalog에 등록된 시나리오와 실제 Content.json을 사용한다. 원작 분석용 배치 CSV를 원작의 확정 배치로 자동 적용하지 않는다.

- 시나리오 선택: 전용 preview scene에 타일맵을 로드한다. 사용자가 열어둔 씬을 교체하거나 저장하지 않는다.
- 빨간 표식: Content.units의 몬스터. 가능한 경우 실제 방향 그림을 표시하고, 그림이 없으면 색상 표식과 ID/이름을 표시한다.
- 파란 표식: 게임 진입 entryX/entryY. 드래그하거나 우측 좌표 입력으로 변경한다.
- 전투 배치 / 연출 배치는 상호 배타적 토글이다. 전투 모드는 몬스터·진입점·상자/이벤트를, 연출 모드는 intro의 CHARPOS만 표시한다. 전환 시 선택과 드래그 상태를 초기화하며 배치 데이터는 바꾸지 않는다.
- 연출 배치는 읽기 전용으로 확인한다. 목록 클릭으로 해당 NPC 위치로 화면을 이동할 수 있다. 확대·축소·가운데 드래그는 두 모드에서 모두 사용한다.
- 노랑 표식: 상자 관련 MESSAGE가 있는 이벤트의 CHANGESPRITE 좌표. 그림 교체 좌표가 없으면 CHARPOS 발동 조건 칸을 사용한다.
- 보라 표식: 퀘스트/이벤트의 CHARPOS 발동 조건 칸. 퀘스트 전용 데이터가 있는 것으로 추측하지 않으며 이벤트 번호·scope·mode를 툴팁/목록으로 표시한다. 상자/이벤트는 읽기 전용이고 목록 클릭으로 해당 위치를 볼 수 있다.
- 몬스터 선택: 맵 클릭 또는 우측 목록. 드래그하면 원본 좌표(좌상단0,0)에 맞춰 이동한다. 원본좌표에서 world Y는 height-1-y로 변환한다.
- 몬스터 추가: 직업 ID와 웨이브를 지정하고 추가한다. 중복되지 않는 유닛 ID로 생성한다. 이름·직업·좌표·웨이브·기본 전투 수치를 편집한다. 추가한 몬스터의 HP 등은 실제 사용할 값으로 입력한다.
- 삭제: 선택 후 삭제 버튼 또는 텍스트 편집 중이 아닐 때 Delete.
- 웨이브: 기본값은 현재 웨이브만 표시. 모든 웨이브를 켜면 전체를 표시한다. 기본 이름은 숨기고 선택/툴팁으로 확인하며 이름 토글로 전부 표시할 수 있다.
- 탐색: 휠로 커서 기준 확대·축소(0.5~8배), 가운데 마우스 버튼을 누른 채 드래그해 화면 이동. 슬라이더도 사용 가능하며 전체 보기로 원위치/배율을 복원한다. 이동은 배치를 변경하지 않는다.
- 뷰어: 타일맵·그리드·몬스터·라벨·이벤트 표식을 같은 영역으로 잘라서 표시한다. 몬스터와 선택 판정 크기는 타일의 화면 크기를 따라 확대·축소된다.
- 저장: 실제 Resources/Scenarios/{key}/Content.json의 units·entryX·entryY·profileHash를 갱신한다. 대사·이벤트 등 나머지 루트 필드는 그대로 보존한다. 외부 수정 충돌·범위 밖 좌표·잘못되거나 중복된 ID는 저장 거부한다. 닫기/시나리오 전환 시 미저장 변경 확인을 제공한다.

저장한 배치는 콘텐츠 데이터에 반영된다. 원작 복원 정책상 로컬 서버가 배치를 결정하지 않는 모드에서는 이 편집기가 서버 등장 통지를 새로 만들지는 않는다. 삭제한 유닛 ID를 참조하는 이벤트/대사는 자동 수정하지 않는다. entry는 도입 연출의 CHARPOS/CHARMOVE를 변경하지 않는다. 배치 해시 변경 후 기존 진행 저장은 콘텐츠 불일치로 거부될 수 있으므로 별도 검증 저장을 사용한다.

검증: 전체 Runtime 소스와 새 EditorWindow를 Unity 참조 DLL로 보조 컴파일해 오류0 확인. 실제 저장 배열 교체 함수로 중첩 배열·문자열 속 괄호·빈 배열·비배치 필드 보존·필드 누락 거부 검사 통과. 실제 Unity 창의 렌더링·마우스 드래그·디스크 저장/재열기·플레이 반영은 이 환경에서 실행하지 않았다.

현재 몬스터 좌표의 출처: 편집툴이 자동으로 새 배치한 것이 아니라 실제 Content.json을 읽는다. 01~17에는 이전 싱글판 보완 좌표 및 Unity 충돌 회피 조정이 포함된다(01의 placementAdjustments 등). 원작 확정 배치 전체를 적용한 것으로 판단하면 안 된다. 분석 전용 SET/POS CSV로 자동 덮어쓰지 않으며 이번 변경으로 몬스터 좌표를 재배치하지 않았다.

후속 검증: 변경된 편집툴과 전체 Runtime을 Unity DLL 참조로 보조 컴파일해 오류0 확인. 25개 Content.json을 조사해 상자 후보44곳·기타 이벤트 조건231곳을 확인(중복 이벤트의 같은 위치는 별도 표식일 수 있음); 01은 상자7곳·기타10곳·몬스터33개. 실제 마우스/렌더링 검증은 미실행이다. Unity에서 휠 커서 기준 확대→가운데 드래그→뷰어 경계 잘림→몬스터 크기/선택 판정→웨이브 필터→상자/이벤트 목록 이동→편집/저장 복원을 확인한다.

## 실제 전투 배치 정돈

01~17의 Content.units 좌표를 무리 단위로 정돈했다. 3마리 무리의 삼각형/일렬 대형과2칸 간격을 적용하고, 가능한 통행 영역과 이벤트 칸·진입점 주변을 검사했다. 336무리·1008마리 중870마리가 이동했다. 편성/수치/웨이브·연출은 유지하며, 이번 좌표도 사용자가 요청한 편집 배치로 구분한다. 33 이후와 원본 분석 SET/POS는 자동 변경하지 않는다. 도구에서 다시 불러오면 변경된 좌표를 확인할 수 있다. 전후 기록·검사·재적용 방법은 `Tools/ScenarioPlacementChecks/README.md`를 참조한다.

## 수련장·대련장과 배치 근거 비교

- 선택 목록에 수련장101~107(20×15), 사용자 확인 대련장201~207(30×30)을 추가했다. 각 항목은 실제 Map_{id}_; 씬을 미리 보여준다.
- 수련장·대련장의 배치는 편집 전용 `Assets/_Game/Editor/BattleLayouts/Training{id}.json`, `Duel{id}.json`에 저장/재로드한다. 최초에는 서버의 배치를 만들어내지 않고 빈 목록과 중앙 진입점으로 연다. 몬스터 추가/이동/삭제는 동일하게 사용한다. 로컬 서버 패킷에 이 파일을 자동 적용하는 기능은 포함하지 않는다.
- 시나리오는 기존 Content.json 편집을 유지한다. 두 저장 경로를 혼동하지 않도록 창에 표시한다.
- 헤더·그룹별 선택 정보·지도 크기/유닛/웨이브 요약·검사 패널을 추가해 구성했다.
- `AI 영역 비교`를 켜면 해당 시나리오 원본 .ai의 AREA 중심과 범위를 청록 표식으로 비교한다. 사각형은 반경 범위 참고선이며 원작의 정확한 거리/타깃 판정 형태 또는 출현 지점으로 해석하지 않는다. 현재 웨이브의 몬스터 배치와 달리 AI 영역은 원문 전체를 표시한다. 분석 파일이 없는 항목은 영역을 표시하지 않는다.

배치 재해석 결과는 `분석/Saver_Late/placement_interpretation_comparison.json`에 보존했다. 원본 SET/POS610개는 ID 십단위로 묶으면122개 무리가 모두5마리다.65개 무리는 선두(0,0)+주변(±1,±1) 모양이다. 이는 이전에 편집한01~17의3마리 대형을 원작 사실로 볼 수 없음을 뒷받침한다. ID 십단위 묶음은 데이터 비교 방법이며 실제 서버 편성 API를 증명하는 것은 아니다.

동일 자료의 좌표 가설 비교: 원문 x/y 절대 좌표는610개 모두 맵 안, x/y 뒤집기는560개, 선두 좌표를 다시 더하는 상대좌표 가설은130개만 맵 안이다. 범위 검사만으로 축 방향/모든 의미를 확정하지 않는다. 특히01~17의 원본 SET/POS 편성이 없는 상태에서5마리로 임의 증원하거나 AI AREA를 생성 좌표로 바꾸지 않았다.

검증:14개 맵 씬 존재 확인. 전체 Runtime+변경된 편집툴 보조 컴파일 오류0. 네이티브610좌표/122무리의 대안 가설 비교 도구 실행. 실제 Unity 창의 조작·새 편집 JSON 저장/재로드는 미실행이다.

## 무리 형태 비교 보기

`무리 경계` 기본 표시로 각 무리에 다른 색의 테두리·연결선·W/G 번호·개체 수를 표시한다. 몬스터의 선택 경계도 해당 무리 색으로 표시한다. 필터에서 한 무리만 선택하면 맵과 우측 목록이 같이 좁혀진다. 모드/무리 기준/필터를 바꿀 때 숨겨진 개체를 편집하지 않도록 선택을 초기화한다.

- ID 구간 기준: 같은 웨이브의 ID 십단위 구간으로 묶는다. 현재01~17의 보완 편성 구조와 원본 POS 자료를 비교하는 방식이며 서버의 공식 무리 식별자를 뜻하지 않는다.
- 가까운 AI 중심: 같은 웨이브에 실제 존재하는 AI 명령 유닛의 AREA 중심 중 제곱거리 최소인 곳으로 묶는다. 동률은 ID순이며 AI 자료가 없으면 ID 구간으로 돌아간다. 이 거리 기준은 비교 가설이고 원작 AI 거리 공식을 복원했다고 표시하지 않는다.
- 두 기준 모두 표시용이다. 좌표·몬스터 수·웨이브·이벤트·그룹 소유 관계를 JSON에 추가하거나 바꾸지 않는다. 원본5마리 형태가 발견되었다는 사실만으로01~17을 임의 증원하지 않는다.
- 연결선은 표시 묶음의 선두 후보와 구성원을 연결한다. 실제 전투 지휘 관계를 증명하지 않는다. 각 무리의 경계/연결선/라벨도 지도 뷰어 안으로 잘라 표시한다.

검증:전체 Runtime+편집툴 보조 컴파일 오류0. 실제 Unity의 무리 구분 가독성·필터 선택·클리핑은 미실행이다. 전투/연출 토글 및 저장 기능은 동일하게 유지한다.

## 선두·지원 구성과 브르고스궁 늑대 재대조

사용자 기억의 「대장1+쫄병2~4」를 기준으로 원본 그룹을 재대조했다. 회수한 SET/POS122무리는 모두5마리이며113무리의 첫 레코드에 추가값1,8무리는3,1무리는 추가값이 없다. 나머지4레코드는 추가값이 없는 패턴이다. 첫 레코드+주변4마리 구성은 지지하지만 추가값을 대장 플래그·단수·지원 수로 확정하지 않는다. 원본 모든 시나리오가5마리로 고정이라는 주장도 하지 않는다.

편집툴은 선두 후보를 별표로 표시한다. AI 중심 비교에서도 AI 명령이 명시된 유닛은 자기 중심으로 보존하고 지원 후보만 가까운 중심에 연결한다. 이는 표시 가설이며 실제 무리 지휘/생성 관계를 JSON에 새로 확정하지 않는다.

원본 ability/그림 대조:

|301|와일드독|갈색 네발형|01.deo의 CHARPOS에 존재|
|401|들개|파란 네발형|01.deo의 CHARPOS에 존재|

|701|키스라|칼을 든 붉은 직립형|01.deo에서 유닛700으로 명시|

기록:`분석/Saver_Late/brugos_monster_role_review.json`. 그림 비교:`Tools/ScenarioPlacementChecks/brugos-wolf-candidates.png`. 실제 좌표·편성·수량·수치는 이번 검토에서 변경하지 않았다.

## 부대 소속·실제 대형·AI 이동 기준을 분리한 재해석 (2026-10-31)

이번에는 가까운 점을 묶는 방식에서 벗어나 **원본 코드의 지휘관 소속 → SET의 실제 구성원 → POS의 실제 칸 → AI의 이동 기준** 순서로 해석했다. [구조 분석 JSON](../분석/Saver_Late/troop_structure_review.json), [비교 화면](../Tools/ScenarioPlacementChecks/troop-structure-view.html), [대형/오분류 비교 그림](../Tools/ScenarioPlacementChecks/troop-structure-comparison.png)에 결과를 기록했다. 편집툴의 몬스터·게임 데이터는 이번 분석으로 재배치하지 않았다.

### ID 구간은 후기 코드에서도 확인되는 지휘관 관계

후기 `userunit.dll` SHA256 `74b2e0489b1025b03fceb5ad74163d1f07c139d394abe1ee2554b26ba837559b`를 직접 대조했다.

- `_ai:10002444`는 ID를10으로 나눈 나머지가0이면 ExecuteCommanderAI, 나머지이면 병사 AI로 분기한다.
- `setmonsterai:100015a4`와 병사 이동 경로 `100035e9`는 비음수 ID에 대해 `ID/10*10`으로 지휘관 슬롯을 구한다. 예:400→지휘관,401~409→400번 지휘관 참조다.
- `10003634..10003662`는 그 지휘관의 현재 좌표와 병사의 맨해튼 거리를 계산해 지휘관 레코드+4C와 비교한다. 가장 가까운 다른 지휘관을 새 소속으로 고르는 계산이 아니다.

따라서 앞 절의 「ID 구간 기준은 비교 방법」이라는 설명을 보완한다. **이 후기 클라이언트의 지휘관/부하 연결은 코드 근거가 있다.** 다만 이는 서버의 편성 API, 설치된 SET/POS의 자동 로드, 모든 슬롯의 실제 출현을 증명하는 것은 아니다. 끝자리1~9가 같은 지휘관을 참조할 수 있다는 구조와 실제 사용되는 부하 수는 구분한다.

### 원본 POS는 네 가지 대형을 담는다

SET/POS가 연결되는16맵의610마리/122부대는 모두 지휘관 슬롯0+부하 슬롯1~4다. 지휘관 좌표를(0,0)으로 뺀 **관측 상대 모양**은 다음과 같다. 원문 좌표 자체를 상대값으로 다시 더하는 방식은 사용하지 않는다.

| 대형 | 지휘관을 제외한 상대 좌표 | 관측 부대 |
| --- | --- | ---: |
| 대각 네 귀퉁이 | (-1,-1),(-1,1),(1,-1),(1,1) | 65 |
| 상하좌우 | (-1,0),(0,-1),(0,1),(1,0) | 44 |
| 좌우+아래2칸 | (-1,0),(1,0),(0,1),(0,2) | 12 |
| 지휘관 뒤 V형 | (-1,1),(1,1),(-2,2),(2,2) | 1 |

위 표는 좌표 집합의 분류다. 구성원별 슬롯 순서는 JSON에 별도 보존했다. 예를 들어51번의510부대는511=(-1,0),512=(1,0),513=(0,1),514=(0,2)이다. 모양을 예쁘게 정렬하려고 슬롯을 교환하지 않는다. 관측된122부대를 원작 모든 시나리오의5인 고정 규칙으로 일반화하지 않는다.

### 가까운 AREA를 소속/출현 기준으로 쓰면 잘못 묶인다

원본에 POS와 AREA 중심이 다른6건이 있으며, 세 쌍의 지휘관 중심 좌표가 서로 엇갈려 있다. 의도적인 이동 영역인지 자료 오류인지는 이 사실만으로 결정하지 않는다.

| 맵 | 지휘관 | POS | AI AREA 중심 |
| --- | ---: | --- | --- |
| 26 | 490 | (36,3) | (10,7) |
| 26 | 700 | (10,7) | (36,3) |
| 52 | 480 | (12,10) | (19,6) |
| 52 | 700 | (19,6) | (12,10) |
| 53 | 500 | (35,25) | (18,21) |
| 53 | 700 | (18,21) | (35,25) |

현재 편집툴의 근접 가설과 같은 정책(지휘관 자기 ID 유지, 부하는 가장 가까운 AREA)을 원본에 적용하면 **24마리가 다른 지휘관으로 묶인다.** 그러므로 가까운 AREA를 부대 소속의 복원 기준으로 채택하지 않는다. 또한 기존 비교기의 정규식이 `AREA (`처럼 괄호 앞에 공백이 있는 표기를 누락했음을 확인해 분석 도구를 수정했다. 현재 편집툴의 같은 정규식/표시는 이번 분석 작업에서는 변경하지 않았다.

`SOILDER(700)`도 소속 변경 명령이 아니다. 후기 `CommanderAIMove:10004932..1000497c`는 대상700의 현재 좌표+70/+74를 이동 영역의 기준으로 읽고 반경은 `max(대상+4C,7)`로 사용한다. AREA는 고정 영역, SOILDER는 유닛을 따라 움직이는 영역 기준으로 구분할 수 있다. 전체 AI에서 AREA1099행·SOILDER22행이다. 시나리오01의480·490은700을 이동 기준으로 참조하지만, 각 부대의 부하를700 소속으로 다시 합치는 근거가 아니다.

### POS만 있는 슬롯과 현재 보완 배치를 구분

SET과 연결되지 않는 POS205행 중195행은400미만의 슬롯이고, 나머지10행은26의475/476,51의705/706,53의425/426/705/706,55의705/706이다. 위치 칸이 더 준비되어 있어도 SET 정의가 없는 몬스터를 추가 생성하지 않는다. 이를 사용하지 않는 예약·초안 슬롯일 가능성과 실제 출현 몬스터라고 확정하는 주장은 구분한다.

현재01~17은336묶음/1008마리의3인 보완 편성이다. 원작 초기 SET/POS를 읽어 만든 편성이 아니므로 원본4종 대형과 소속 구조를 확인했다고 이 수량·직업·좌표까지 복원된 것은 아니다. 또한 서로 다른 웨이브가 같은 칸을 사용하는 곳이105칸(01은0,17은23) 있어 전체 웨이브를 함께 표시하면 혼잡해질 수 있다. 같은 시점의 배치 중복과 구분한다. 비교 화면은 원본과 현재 보완 배치를 따로 선택하고 웨이브별로 확인할 수 있게 했다.

검증:16맵 SET/POS의 소스 해시·숫자 행 연결·610좌표·122지휘관 슬롯을 재검사했다. 후기 export/opcode 및 비음수ID0~999의 나눗셈 산술 모델 검사가 통과했다. 실제 원작 실행/AI 에뮬레이션 결과로 취급하지 않는다. 도구 실행 전후01~17 Content.json 해시를 보존했다.

Python 구문·JSON 집계·문서 링크/공백·HTML JavaScript 구문 검사가 통과했다. 원본16맵+현재17맵의 두 묶음 모드/웨이브0 표시를 DOM fixture에서99회 호출해 유한한 좌표 출력을 확인했다. PNG는 생성 후 시각 확인했다. 이 검사는 Unity 편집툴 실행이나 실제 브라우저의 화면/마우스 검증으로 계산하지 않는다.
