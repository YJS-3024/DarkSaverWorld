| 본문 오프셋 | 원본 필드 |

`43B5B0`은 이전 전송 버퍼를 초기화한다. `43B6D0`은 입력/출력을 각 선언 길이+1로 할당하고 CRC를FFFFFFFF로 시작한다. `43B7B0`은 `478930`을 입력43B2F0/출력43B390 콜백과0x8DD8 작업 공간으로 실행한다. 출력 콜백의477E10은 IEEE CRC32 표491370을 사용하고 최종 XOR를 하지 않는다. 따라서 일반 `zlib.crc32` 결과의보수와 같다. 추론된 void 반환형으로 CRC 계산이 사라진 초기 디컴파일은 사용하지 않는다. 3개 인수(data,count pointer,previous CRC pointer)·DWORD 반환을 복구한 export와 원본 어셈블리를 보존했다.

이 정보는 외부 자동 압축 해제 프로그램의 구조이며 게임 엔진이나 실제 게임 코드의 구조를 뜻하지 않는다. NE 형식이므로 최신 64비트 Windows에서는 외부 설치 실행부가 직접 동작하지 않을 수 있다.

ZIP 호환 중앙 디렉터리에서 14개 항목을 확인했다. 전체 원본 크기는 18,868,234 bytes, 압축 크기는 18,317,389 bytes다.

## 설정에서 확인된 내용

- 설치 언어 선택 창이 활성화되어 있다 (`EnableLangDlg=Y`).
- 언어 데이터에는 영어, 한국어, 일본어를 포함한 여러 언어 항목이 있다.
- 지원 OS 표에는 Windows 3.1/3.11, Windows 95, Windows NT 3.51/4.0 계열이 기록되어 있다.
- 설치 패키지는 구형 InstallShield 계열 형식을 사용한다.

지원 OS 표는 설치 도구가 가진 공통 플랫폼 목록일 수 있으므로, Saver가 그 운영체제를 모두 실제 지원했다는 뜻으로 단정하면 안 된다.

## 정적 분석의 범위와 한계

설치본과 클라이언트에서 확인 가능한 파일·데이터·공개 심볼·주요 실행 흐름은 추출했다. 다만 서버 실행 파일이 없으므로 피해·명중·보상·레벨업의 권위 판정 공식은 복원 대상 자체가 설치본에 존재하지 않는다. LSC/LCE/LNM/LTN의 일부 가변 필드와 사용되지 않는 런타임 레코드 바이트도 원래 제작 도구나 런타임 계측 없이 이름을 확정할 수 없다. 영역별 종료 상태와 근거는 `catalogs/analysis_completion_matrix.csv`에 정리했다.

이번 작업은 악성 코드 안전성 보증이 아니며, 저작권·라이선스·분석 권한은 기술 분석과 별도로 확인해야 한다.

## CAB 추출 후 확인 결과

InstallShield 5 이상을 지원하는 오픈소스 `unshield 1.6.2`로 `data1.cab`을 읽었다. 배포 파일의 SHA-256은 Scoop 공개 매니페스트의 값과 일치했다. CAB에는 1,175개 항목이 있고, 중복 경로를 덮어쓴 실제 추출 결과는 837개 파일, 총 39,016,993 bytes다.

### 실행 코드

- `Saver.exe`: 389,120 bytes, `NewDark` MFC 응용 프로그램
- `DManage.dll`: 90,112 bytes
- `GameCtl.dll`: 122,880 bytes
- `setunit.dll`: 36,864 bytes
- `userunit.dll`: 106,496 bytes
- `Compress.dll`, `soundll.dll`

원본 C/C++ 소스는 포함되어 있지 않다. 실행부는 MFC 기반 네이티브 코드이므로 이후 확인은 디스어셈블과 의사코드 복원 방식으로 진행해야 한다. 원래 변수명, 주석, 클래스 구조는 복원할 수 없다.

### 게임 데이터 후보

| 목적 | 우선 분석 대상 | 현재 판단 |
|---|---|---|
| 직업·성장·경험치 | `Glib/GameLib.ltn`, `.lce`, `.lnm` 및 `Saver.exe` | 32비트 정수 레코드가 반복되는 바이너리 데이터 |
| 아이템 | `gameres/item.arc`, `GameLib.*` | `item.arc` 안에 `Item.bmp` 등 다수 항목이 든 자체 ARC 형식 |
| 몬스터·NPC | `gameres/char*.arc`, `Glib/Wlib`, `MAP/*set.arc` | 캐릭터 리소스와 장면·배치 데이터가 분리된 구조로 추정 |
| 맵 배치 | `MAP/*.mrc`, `MAP/*set.arc` | `.mrc`에 폭·높이로 보이는 값과 격자 데이터가 있으며, `set.arc`에는 `.AI`, `.DEE` 등의 내장 항목이 있음 |
| 지형·충돌 보조 | `MAP/*hmap.bmp` | 맵별 높이/충돌 마스크 후보 |

### 대표 맵 구조 단서

`MAP/01.mrc`는 처음에 32비트 정수들이 이어지고 헤더 부근에 `40, 40`이 존재한다. 뒤이어 `0x65` 값이 반복되는 격자형 데이터가 나타난다. 따라서 40×40 크기 또는 레이어 폭·높이일 가능성이 있지만, 레코드 의미는 아직 검증되지 않았다.

`MAP/01set.arc`는 버전 문자열로 보이는 `0901` 뒤에 길이 접두 파일명 `01.AI`, `01.DEE` 등이 이어진다. `gameres/item.arc`도 같은 `0901` 구조와 `Item.bmp`, `HEADEND` 항목을 가지므로 공통 ARC 컨테이너로 판단된다.

## 권장 분석 순서

1. ARC 컨테이너의 파일명·오프셋·압축 크기 구조를 먼저 확정한다.
2. 대표 맵 하나(`01.mrc`, `01set.arc`, `01hmap.bmp`)를 동일 좌표 기준으로 비교한다.
3. 맵 배치 포맷이 검증된 뒤 전체 맵을 CSV/JSON으로 변환한다.
4. `GameLib.*`와 실행 코드의 읽기 함수를 교차 확인해 직업·경험치·아이템·몬스터 레코드 구조를 확정한다.

## ARC 헤더 분석 결과

`0901` ARC의 파일 목록 영역은 버전 문자열 뒤에 36바이트 고정 레코드가 반복되고 `HEADEND` 레코드로 끝난다. 각 항목에서 다음 값을 검증했다.

- 최대 16바이트 파일명
- 원본 크기와 압축 크기
- 압축 데이터 시작·끝 오프셋
- 압축 데이터 바이트 합의 하위 16비트 체크섬

`MAP/01set.arc`의 5개 항목(`01.AI`, `01.DEE`, `01.DEO`, `01.evt`, `01.srf`) 모두 저장 체크섬과 실제 계산값이 일치했다. 압축 해제 전에도 파일 경계와 손상 여부를 안정적으로 확인할 수 있다.

`gameres/set.arc`에서는 다음 핵심 데이터가 확정됐다.

| 파일 | 원본 크기 | 예상 내용 |
|---|---:|---|
| `itemtbl.atr`, `itemtbl1.atr` | 163,704 / 164,791 | 아이템 테이블 |
| `ability.atr`, `ability1.atr` | 64,685 / 64,704 | 능력치·직업 관련 테이블 후보 |
| `levelptl.atr` | 1,892 | 레벨별 포인트/경험치 후보 |
| `levelabl.atr` | 166,915 | 레벨별 능력치 후보 |

| `Magictbl.atr`, `MagicPtn.atr`, `magicatr.atr` | 30,127 합계 | 마법 정의와 패턴 후보 |

실행 코드 문자열과 내보낸 심볼에서도 `GetItemTable`, `SetExp`, `setmonsterai`, `GetUnitInfoP`, `mainmapgetchar`, `GetTilePtr`가 확인됐다. 따라서 아이템·경험치·몬스터·맵 시스템이 각각 위 외부 테이블 및 맵 파일을 읽는 구조임은 확실하다.

ARC 본문 압축은 `Compress.dll` 내부의 `ELzrw1KHCompressor`와 `UnpackAFile`이 처리한다. 일반 Deflate가 아니며, 로더는 압축 형식 값에 따라 LZRW1/KH 계열과 별도 방식들을 선택한다. 다음 단계는 이 함수의 데이터 입출력 규칙을 복원해 `.atr`와 맵 배치 하위 파일을 실제로 압축 해제하는 것이다.

## ARC 본문 압축 해제 결과

`Compress.dll`의 32비트 공개 함수 호출 규약을 복원했다.

- `OpenArcFile(path)`: ARC 열기
- `UnpackAFile(name)`: 지정 항목을 내부 버퍼로 압축 해제
- `GetPointer()`, `GetBuf2Size()`: 결과 주소와 크기 반환
- `CloseArcFile()`: ARC 닫기

32비트 보조 프로그램으로 `gameres/set.arc`의 15개 항목과 `MAP/01set.arc`의 5개 항목을 원본 크기대로 추출했다. `levelptl.atr`의 추출 크기는 헤더에 기록된 1,892 bytes와 일치한다.

### 확인된 데이터 스키마

- `ability.atr`: 직업 ID·직업 그림·기본/한계 능력치·이동력·명중/회피·병종·획득 경험치·전직 목록·이름·설명
- `levelabl.atr`: 직업·레벨별 능력치 증가·포인트·다음 직업·획득 경험치·요구 경험치·마법·기술
- `levelptl.atr`: 직업별 능력치 성장 계수와 전직 제한
- `itemtbl.atr`: 아이템 ID·그림·장착 조건·직업별 사용 가능 여부·가격·각종 보정·이름·설명
- `solskill.atr`: 특수 기술·레벨·고용 가능 용병 종류와 수

UTF-8 CSV 변환 결과는 각각 직업 521행, 직업/레벨 2,271행, 성장 계수 70행, 아이템 1,180행, 특수 기술 64행이다. 원본의 독립된 연속 행과 `;999` 종료 표식은 표 변환에서 제외했고 원본 추출 파일에는 그대로 보존했다. 경험치 표는 276개 직업 ID, 레벨 1~100 범위를 포함하며 각 직업 안에서 요구 경험치가 역행하는 행은 없다. 최대 저장값은 3,477,000,000이므로 이식 시 부호 있는 32비트 정수로 읽으면 안 된다.

사용 편의를 위해 `catalogs/experience_progression.csv`에는 직업 이름과 레벨·요구 경험치·다음 직업·보상·습득 마법을 결합했다. `catalogs/items.csv`에는 1,180개 아이템 원본 필드와 장착 위치 기반 분류를 추가했다. 장착 위치 1~10은 이름 표본상 원거리/지팡이, 무기, 갑옷, 신발, 투구, 장신구/교본, 소비품, 방패, 퀘스트/잡화, 이동/특수 소비품에 각각 대응한다.

### 대표 맵 01 배치

`01.AI`, `01.DEE`, `01.DEO`, `01.evt`, `01.srf`가 CP949 평문으로 복원됐다.

- `01.AI`: 유닛 ID, AI 유형, 활동 영역/추적 대상, 공격·마법·휴식 확률
- `01.DEE`, `01.DEO`: 장면 로드, 유닛 배치 좌표, 이동·방향·공격·대사
- `01.evt`: 이벤트 조건, 보상, 메시지, 스프라이트·타일 변경
- `01.srf`: 맵 이름, 임무와 승리 조건 설명

확정된 명령만 파싱한 `map_01_placements.json`에는 `CHARPOS` 배치 23개와 AI 규칙 11개가 들어 있다.

전체 EVT의 명령 빈도와 대표 블록을 MRC 좌표에 대조했다. 후속 원본 DLL 분석으로 이전 `(y,x)` 해석을 정정했다. `CHARPOS`, `CHARPOS3`, `WARPCHAR`, `MAGIC`과 맵 변경 명령의 좌표는 원문 `(x,y)`를 유지한다. `01.evt`의 `CHANGESPRITE 5 15 ...`는 `01.mrc`의 `(5,15)`에 있는 첫 스프라이트 레코드 63을 가리킨다. DManage `SpriteChange(0x100090D0)`의 인수 전달과 실제 레코드를 함께 확인했으며, 필드 인수 재배열을 좌표 전치로 해석하면 안 된다. 구형 `CHANGETILE` 문법의 실행 여부는 별도로 구분한다. 숫자나 오타처럼 보이는 희소 토큰은 독립 명령으로 확정하지 않고 원문에 보존한다.

## 전체 ARC·게임 데이터 카탈로그

추출된 설치 파일에서 ARC 123개를 확인했다. 버전은 `0901` 120개와 `0720` 3개이며, 내장 항목은 총 1,108개다. 모든 항목의 시작·끝 오프셋과 16비트 바이트 합 체크섬이 일치했다. 전체 압축 해제 결과는 14,587,395 bytes다.

주요 추출 파일은 BMP 508개, AI 104개, 이벤트 104개, 맵 설명 96개, 장면 진입/종료 스크립트 131개, WAV 20개, ATR 테이블 13개다.

### 유닛 분류

`ability.csv`의 ID 범위와 이름을 대조해 다음 카탈로그를 만들었다.

- 플레이어 직업: 100번대, 70개
- 용병: 200번대, 92개
- 몬스터·보스: 300~700번대, 324개
- NPC·특수 유닛: 800번대 이상, 35개

이 분류는 코드의 공식 enum을 복원한 결과가 아니라 데이터 ID 범위, 이름, 맵 사용 패턴을 이용한 분류다. 전체 행은 `catalogs/units_all.csv`에 보존했다.

### 데이터 버전 차이

쌍으로 존재하는 테이블은 단순 복제본이 아니다.

- `ability` / `ability1`: 공통 ID 가운데 143개 유닛의 능력치·획득 보상 등이 다르다. 두 파일 모두 실제 유닛은 521개이며, 과거 집계의 추가 1행은 `;999` 종료 표식임을 검증해 제외했다.
- `itemtbl` / `itemtbl1`: 47개 아이템의 내구도·가격·장착 레벨·이름 등이 다르다.
- `TileAttb` / `TileAttr`: 21개 타일 행의 병종별 공격·방어·이동 보정이 다르다.

따라서 Unity 이식 시 어느 버전이 실제 게임 모드에 사용되는지 호출 인자와 시나리오별 로딩 경로를 확인해야 한다.

## 전체 맵 스크립트 분석

전체 맵에서 `CHARPOS` 배치 845개, AI 규칙 1,134개를 구조화했다. AI 규칙은 활성 파일 923개와 `.BAK` 중복 211개로 구분된다. 스크립트 명령은 확장자별 조합 111종이며 `MESSAGE` 대사는 1,993행이다. 주요 명령에는 `EVENT`, `CHARDEAD`, `SCENECLEAR`, `RANDOM`, `GETITEM`, `MAGIC`, `CHANGETILE`, `WARPCHAR`, `CHARMOVE`, `ATTACK` 등이 있다.

`catalogs/map_unit_placements.csv`는 각 배치의 맵, 좌표, 소유자 ID, 유닛 ID를 유닛 카탈로그의 이름·분류와 결합한다. 배치 845개 중 유닛 ID 696개가 능력치 테이블과 직접 연결되며, 나머지는 장면 전용 변형 ID 또는 스크립트 핸들로 남긴다.

## MRC 바이너리 구조

`DManage.dll`의 `BB_Map::LoadMap` 디스어셈블과 파일 크기를 대조해 `.mrc` 구조를 확정했다.

1. `int32 resourceCount`
2. `int32 resourceIds[resourceCount]`
3. `int32 width`, `int32 height`, `int32 spriteCount`
4. `byte layer1[width * height]`
5. `byte layer2[width * height]`
6. 5바이트 타일 레코드 `width * height`개
7. 16바이트 스프라이트 레코드 `spriteCount`개

예상 크기 공식 `16 + 4R + 7WH + 16S`가 전체 MRC 647개와 정확히 일치했다. `GetTileData`, `TileChange`, `SpriteDraw`, `SpriteChange`까지 대조한 결과 타일은 리소스·그룹·프레임·속성·애니메이션 모드의 5바이트다. 스프라이트는 리소스 인덱스, `int32 x/y`, 그룹·프레임을 가지며 좌표에 32를 곱해 화면 위치로 사용한다. 마지막 2바이트는 두 함수 모두 읽거나 쓰지 않고 파일마다 비정형 값이 남아 있으므로 의미 필드가 아닌 미초기화 패딩으로 확정했다. 전체 40,589개 스프라이트는 `catalogs/mrc_sprites.csv`, 오프셋 근거는 `catalogs/binary_record_layouts.csv`에 저장했다.

GRS의 셀 3,084개에서 이미지 프레임 배열을 `catalogs/grs_cells.csv`로 추출해 MRC의 연결을 복원했다. 앞의 두 바이트 레이어는 모든 칸에 먼저 그리는 `배경 GRS 번호 → 기본 타일 번호`이고, 5바이트 레코드는 그 위에 합성하는 장식·애니메이션 타일이며 스프라이트가 마지막에 그려진다. 장식 그룹 `0xFF`는 빈 바닥이 아니라 추가 장식이 없다는 뜻이다. 원본은 각 비트맵 표면에 `SetColorKey(0)`을 호출하므로 RGB 검정만 투명해지고, 검정이 아닌 디더 그림자 픽셀은 유지된다. 전체 647개 맵의 타일 776,984개와 스프라이트 40,589개를 검사했으며, `tools/Render-SaverMrc.ps1`로 대표 `01.mrc`를 1280×1280 PNG로 복원했다. 출력은 `unpacked/map_previews/01.png`, 전체 참조 검사는 `tools/Test-SaverMrcReferences.ps1`로 재현할 수 있다.

### 동적 캐릭터와 철창 합성 순서

`Saver.exe`의 프레임 단계 콜백은 `_UpdateCharacter(0)`, `_UpdateCharacter(1)`, `BBDX_MapManager::SpriteDraw`, `_UpdateCharacter(2)`를 각각 분리해 둔다. `userunit.dll::_UpdateCharacter`를 대조하면 모드 0은 타일별 유닛 인덱스 표를 갱신하고, 모드 1은 화면 타일을 행·열 순회하며 유닛 본체 함수(`0x1000FCB0`)를 호출한다. 그 다음 `SpriteDraw`가 철창을 포함한 MRC 스프라이트를 합성하며, 모드 2는 상태 플래그 `0x40`이 있는 유닛의 이름·수치 등 보조 표시 함수(`0x1000F950`)를 다시 호출한다. `SpriteDraw`는 Y 좌표로 재정렬하지 않고 파일 레코드 순서를 그대로 사용하며, 화면과 교차하는 레코드 인덱스만 캐시한다. 따라서 철창 안 NPC의 본체는 `바닥/장식 → NPC 본체 → 철창(MRC 스프라이트)` 순서로 가려지고, 같은 패스의 전경 오브젝트끼리는 MRC 저장 순서가 곧 그리기 순서다. Unity 이식에서도 캐릭터 전체를 단일 최상위 Sorting Layer에 두지 말고 이 패스를 분리하고, MRC 스프라이트의 원본 인덱스를 보존해야 한다. 분석 재현 도구는 `tools/Inspect-SaverRenderCalls.py`다.

모드 1의 본체 함수는 유닛 상태 플래그에 따라 일반 본체, 활성 동작, 캐릭터 결합 효과를 분기한 뒤 보조 표시 함수를 호출한다. 따라서 마법·피격·사망 표현을 모두 맵 스프라이트로 취급하면 안 되며 유닛 상태에 붙는 효과는 캐릭터 패스 안에서 처리해야 한다. 반대로 철창·상자 같은 MRC 스프라이트는 그 뒤에 그려진다. 개별 상태 비트의 게임상 이름은 심볼이 없어 추측하지 않았고, 확인된 패스 경계는 `catalogs/render_passes.csv`에 기록했다.

다만 `01.mrc`에서 보이는 두 철창 안의 작은 인물은 동적 NPC가 아니라 철창과 한 이미지로 합쳐진 `mdsr101.grs` secondary 그룹 31, 프레임 0(32×32)이다. 이 합성 프레임은 MRC 스프라이트 인덱스 24·25로 각각 타일 `(15,5)`, `(24,5)`에 배치된다. 같은 위치에 독립 `CHARPOS` 유닛은 없으므로 Unity 복원 시 이 인물을 별도 NPC로 중복 생성하면 안 된다. 같은 합성 프레임은 `01/01t/28/28t` 네 맵에서 총 12회 사용되며 `catalogs/embedded_scene_characters.csv`에 분리했다. `01.evt`의 이벤트 60·61은 주변 위치와 아이템을 검사해 대사 후 캐릭터 ID 800·810을 제거하지만 철창 프레임 자체를 교체하지 않으므로, 화면 장식과 이벤트용 캐릭터 상태는 별도 데이터로 취급한다.

### 물 타일의 캐릭터 잠김 표현

`userunit.dll`은 현재 좌표의 MRC 타일 레코드에서 오프셋 `+3`의 속성 바이트를 읽고 `0x7F`로 마스킹한다. 판정 함수 `0x1000AC90`은 속성 `0x06`과 `0x14`에서 특수 렌더 경로를 반환한다. 이 경로는 캐릭터 본체를 그린 뒤 `gameres/etc.arc`의 `MCURSOR.BMP` 하단에 있는 `(0,32,32,32)`와 `(32,32,32,32)` 수면 프레임을 전경에 추가 합성한다. `GetTickCount / 250ms`의 하위 비트로 두 프레임을 교대하며 캐릭터 기준 Y에 5픽셀을 더한다. 따라서 물에 들어간 캐릭터는 별도의 잠긴 전신 프레임으로 교체되는 것이 아니라 하단이 움직이는 수면 오버레이에 가려져 반쯤 잠긴 것처럼 보인다. 유닛 상태 값 1과 유닛 ID 899는 이 효과에서 제외된다. `FourStepTileDraw`의 네 단계는 전후 레이어 분리가 아니라 화면 영역을 네 구역으로 나누는 처리이므로 Unity에서는 이를 모방할 필요가 없다. 두 프레임은 `unpacked/effects/water_submerge/`에 추출했고 복원 규칙은 `catalogs/tile_visual_effects.csv`에 기록했다.

### 타일 속성 사용과 가림 비트

`TileAttr.atr`에는 `0`~`Q`의 27개 지형 정의와 병과별 공격·방어·이동 수치가 있지만, 전체 MRC 647개의 776,984타일에는 마스크 기준 15종만 저장되어 있다. 물 잠김 속성 `0x06`은 43개 맵의 40,074타일에서 사용되고, 코드가 함께 처리하는 `0x14`는 파일에는 없어 예약 또는 런타임 변경 경로다. `BB_Map::TileAttrChange`는 각 MRC 스프라이트의 이미지 크기가 덮는 타일 범위를 계산해 속성에 `0x80`을 더한다. 따라서 상위 비트는 지형 종류가 아니라 `sprite footprint occlusion`이며, 캐릭터 렌더러는 지형 판정에는 `& 0x7F`를 사용하고 가림 패스 선택에는 상위 비트를 따로 사용한다. `setunit.dll::GetAttrTable2`는 상위 비트를 제거한 값이 `0x1B`보다 크면 속성 0으로 강제하므로 `0x30`, `0x7E`, `0x7F`는 별도 지형이 아니라 기본 지형 0으로 폴백하는 편집기 센티널이다. 원시값별 타일·맵 사용량과 런타임 해석값은 `catalogs/mrc_tile_attribute_usage.csv`, 재생성은 `tools/Build-SaverTileAttributeCatalog.ps1`에 기록했다.

## 그래픽·음원 및 전용 라이브러리

압축 해제된 ARC 리소스 1,108개를 `catalogs/asset_manifest.csv`로 목록화했다. 구성은 표/스크립트 571개, BMP 508개, WAV 20개, RBM 효과 마스크 8개, 실행 파일 1개다. BMP의 주된 규격은 96×128(250개), 64×64(124개), 96×192(71개), 192×256(53개)로 유닛 프레임·아이콘·확대 프레임 묶음에 대응한다. RBM은 16바이트 헤더 뒤 단일 바이트 마스크이며 `16 + height × stride`가 8개 모두 정확히 맞는다(112×112 5개, 170×172 3개).

설치 디렉터리에는 별도로 MIDI 119개, BMP 119개, MRC 647개, GRS 55개와 장면 라이브러리가 있다. `DManage.dll`의 `LoadGrs`는 `%s\Map\mdsr%d.grs` 형식으로 GRS를 읽으며, 각 GRS 헤더의 첫 두 정수는 32, 32다. 따라서 GRS는 32×32 타일 기반 맵 그래픽 리소스 묶음이다.

설치 BMP는 138×138 79개와 100×100 24개가 대부분이고, 나머지는 640×480~800×600 화면 이미지다. MIDI는 119개이며 82개가 단일 트랙·division 224 형식이다. GRS 로더는 라이브러리 안의 오프셋으로 이동한 뒤 표준 `BM` 헤더 14바이트와 DIB 데이터를 읽는 `LoadFileBitmapFromLib`를 사용하므로, GRS가 BMP 계열 타일을 묶은 컨테이너라는 점도 코드로 확인된다.

`DManage.dll`의 내부 GRS 로더를 추가 복원해 55개 파일 전체를 끝까지 파싱했다. 루트에는 기본 타일 크기와 1·2차 그룹 수가 있고, 각 그룹은 1,024바이트 팔레트와 가변 셀 표, 폭·높이·데이터 길이·예약 워드를 가진 이미지 블록을 포함한다. 이 2바이트 워드는 로더가 건너뛰며 투명색 인덱스가 아니다. 픽셀 행은 Windows BMP와 같은 bottom-up 순서다. 팔레트는 Win32 `PALETTEENTRY`의 RGB 순서이므로 BMP `RGBQUAD`의 BGR 순서로 변환해야 한다. 총 4,010개 블록을 올바른 방향·색상의 팔레트 BMP로 `unpacked/grs/`에 분리했으며 `catalogs/grs_images.csv`에 원본·그룹·크기·예약 워드를 기록했다. 4,010개 BMP의 헤더 크기와 실제 파일 크기는 모두 일치한다. 재생성 도구는 `tools/Expand-SaverGrs.ps1`이다.

`Glib`/`Wlib`에는 LSC 88개, LCE/LNM/LTN 각 2개가 있다. LSC는 맵 타일 포맷이 아니라 장면/UI 객체 라이브러리다. `Saver.exe`는 `gscene%d.lsc`를 조합한 뒤 0xA8바이트 장면 객체를 만들고 공통 장면 로더에 넘기며, 객체 내부에는 위치 사각형·자식 객체 포인터 배열·자식 수·상태 필드가 있다. 17개 최소 장면은 60바이트(15개 little-endian int32) 헤더만 가지며, `game.lsc`와 `scene.lsc`는 별도의 36바이트 빈 루트 형식이다. 더 큰 파일은 같은 헤더 뒤에 가변 자식 컨트롤 레코드가 이어진다. 이로써 용도와 상위 컨테이너 경계는 확정됐지만 컨트롤 종류별 가변 레코드의 필드명은 디버그 심볼·제작 도구 없이 확정할 수 없어 원시값을 유지한다.

LCE/LNM/LTN 6개는 모두 전용 메타데이터 뒤에 파일 끝까지 이어지는 표준 BMP 한 장을 포함한다. 이를 `unpacked/legacy_libraries/`에 BMP와 원시 헤더로 각각 분리했고, 크기·해상도·색 심도는 `catalogs/legacy_library_payloads.csv`에 기록했다. 내장 이미지는 200×330~896×64의 8비트 LCE/LNM과 450×491·450×600의 24비트 LTN이며 전부 BMP 크기 검증을 통과했다. MXF 2개는 각각 82,944 bytes로 288×288 단일 바이트 평면과 정확히 일치하며, 비교용 회색조 BMP를 `unpacked/mxf/`에 만들었다. 반복적인 데이터 열 형태가 나타나므로 완성 이미지보다 마스크·인덱스 표일 가능성이 높다. 원시 헤더와 해시는 `catalogs/legacy_formats.csv`, 설치 파일 전체 메타데이터는 `catalogs/installed_file_manifest.csv`에 보존한다.

`setunit.dll`의 공개 getter 주소 계산으로 런타임 레코드 크기도 확정했다. 아이템 `0x298`(664), 직업 능력 `0x2A4`(676), 신형 마법 `0x140`(320), 패턴 `0x148`(328), 타일 속성 `0x0C`(12)바이트다. 이는 변환된 ATR 자료를 Unity 직렬화 구조와 대조할 때 사용할 수 있다.

유일한 `MAP/2044t.mrtc`는 24바이트(정수 6개) 헤더와 정확히 2,500바이트의 50×50 단일 바이트 격자로 구성된다. 명칭과 위치상 맵 보조 타일/경로 데이터로 판단되지만 각 값의 의미는 코드 참조가 확인되지 않아 원시 값으로 유지한다.

## 퀘스트와 음악 연결

## 내부 코드 구조 추가 분석

`GameCtl.dll::OnPacketReceive`는 수신 버퍼를 내부 디스패처로 넘기며, 디스패처는 첫 바이트 `0x5A~0x7B`와 일부 그룹의 두 번째 바이트를 점프 테이블로 분기한다. 이후 `SetHpDisplay`, `SetMpDisplay`, `SetExp`, `AttackChar`, `Magic`, `MoveCharPath`, `SetTickMenu` 같은 `userunit.dll` 함수를 호출한다. 즉 이 설치본은 전투 결과를 자체 계산하는 완전한 싱글 실행기가 아니라 서버가 판정한 결과를 표시하는 온라인 클라이언트 구조다.

- `SetExp(PGSNEWEXP)`: `int16 unitIndex`와 오프셋 4의 32비트 경험치를 받아 유닛 레코드 `+0x08`에 그대로 기록한다.
- `SetHpDisplay(PGSHPSET)` / `SetMpDisplay(PGSMPSET)`: 수신된 새 값을 각각 `+0x20` / `+0x28`에 기록하고, 새 값-이전 값을 `+0x160`에 남긴다.
- `AttackChar(PGSATTACKFX)`: 공격자·방어자와 효과 값을 받아 양측 상태, 방향, 상대 인덱스 및 애니메이션 필드를 설정한다. 피해·명중·치명타를 산출하는 산술은 없다.
- `Magic(PGSMAGIC)`: 시전자/대상 목록과 마법 번호·좌표를 받아 효과 상태와 시작 시각을 설정한다. 실제 수치 판정은 수신 데이터에 의존한다.
- `SetTickMenu(PGSTICKMENU)`: 행동 가능 상태 비트를 레코드에 반영하며 조건이 맞으면 `AIStart`를 호출한다.

일반 공격 요청은 정확히 10바이트로 직렬화된다. 선두는 `0x5C, 0x82`이고 뒤에는 대상 유닛, 공격 유닛, 양쪽 위치의 지형 속성으로 확인되는 16비트 값 네 개가 온다. 전송 직후 클라이언트는 효과값 0의 `AttackChar`를 호출해 공격 방향과 선행 애니메이션만 시작한다. 실제 HP는 이후 별도 `SetHpDisplay` 패킷의 절대값으로 갱신된다. 사망 통지도 유닛 인덱스 하나만 받으며, `dmKillChar`는 유닛 활성값과 맵 점유를 즉시 제거하고 `dmKillChar2`는 상태 비트 `0x80`을 세워 렌더 가능한 시체 상태로 남긴다. 따라서 공격 동작, 피해 적용, 시체/제거 결정은 하나의 로컬 계산 함수가 아니라 서로 독립된 서버 결과 단계다.

마법 요청은 `16 + 2×대상 수` 바이트이며 선두 `0x5C`, 마법 종류에 따른 `0x89/0x92`, 모드 값, 마법 ID·시전자·좌표·계산 비용·대상 수·16비트 대상 목록을 담는다. `CheckMagicTarget`은 마법표의 대상 유형에 따라 단일 유닛, 위치, 범위 또는 주변 격자를 검사해 이 목록을 만든다. 비용 필드는 `GetMagicTbl` 레코드의 계수와 다섯 수치 필드를 조합해 클라이언트에서도 계산하지만, 최종 MP는 별도 `SetMpDisplay` 절대값으로 수신하므로 비용 승인과 실제 차감은 서버 권한이다. 요청·응답 구조와 확정 수준은 `catalogs/combat_protocol.csv`에 정리했다.

복원 가능한 전체 흐름은 `입력/AI 선택 → 클라이언트 사거리·대상 후보 검사 → 요청 전송 → 선행 동작 표시 → 서버의 공격/마법 효과 통지 → HP·MP 절대값 갱신 → 사망 통지 → 경험치 절대값 갱신`이다. 설치본만으로 확정할 수 없는 것은 명중·피해·치명타·상태이상 성공률과 경험치 분배 공식이다. Unity 싱글판에서는 이 구간만 새 판정기로 구현하고, 나머지 상태 전이와 패킷 필드 의미는 원작 흐름을 그대로 사용할 수 있다.

유닛 배열은 인덱스마다 `0x2E0`(736)바이트 고정 레코드를 사용한다. 확인되거나 유력한 30개 필드 오프셋은 `catalogs/character_record_layout.csv`에 근거와 확정 수준을 함께 기록했다. 이 결과로 원작과 동일한 싱글게임을 만들려면 데이터만 이식하는 것이 아니라, 원래 서버가 담당했던 피해·명중·보상·레벨업 판정기를 새로 구현해야 한다는 점이 확정됐다.

## 캐릭터 진영·동맹별 색상 추가 분석

원본은 캐릭터 전체에 단색 틴트를 적용하지 않고, 같은 `%dr.bmp` 시트의 지정된 16색 영역만 팔레트 인덱스로 교체한다. `userunit.dll!loadcharbmp`(VA `0x1000AF00`)는 `getsnum`(VA `0x1000AD00`)의 결과를 사용하며, 캐시도 시트별 최대 4개 색상 변형을 구분한다.

전투 분기에서 확인된 기본 매핑은 다음과 같다. 색상 명칭은 `char0/100r.bmp`의 실제 팔레트 RGB를 기준으로 한다.

| 관계 판정 | 색상 모드 | 팔레트 영역 | 표시 색상 |
|---|---|---|---|
| 같은 팀 판정 함수 `0x100024C0` 통과 | 0 | `A0~AF` 유지 | 기본 빨강 계열 |
| 위 판정 실패 후 `ally3` 통과 | 3 | `A0~AF` → `D0~DF` | 보라·자주 계열 |
| 두 판정 모두 실패 | 2 | `A0~AF` → `C0~CF` | 파랑 계열 |

`ally3`(VA `0x10002520`)는 팀 ID와 관계 테이블을 검사하며, `SetAllyInfo`(VA `0x10004A60`)가 해당 테이블을 설정한다. 따라서 다른 플레이어가 항상 파랑인 것은 아니며, 전투에서 동맹 판정을 통과하면 별도 보라·자주 계열로 표시하는 근거가 있다. 첫 번째 판정 함수에는 같은 팀 외 일부 특수 팀 ID를 묶는 조건도 있으므로 위 표를 모든 특수 유닛에 대한 소유권 규칙으로 일반화하지 않는다.

실제 교체는 `Compress.dll!ReadArcBmp2`(VA `0x0042CED8`, RVA `0x2CED8`)에서 확인했다. 색상 모드가 1~3일 때 픽셀 인덱스 `A0~AF`에 `모드 × 16`을 더하며, 이 영역 밖 픽셀은 그대로 둔다. 모드 1의 `B0~BF`는 초록 계열이지만, 위 전투 관계 분기에서의 사용 조건은 확인되지 않았다. 비전투 분기는 유닛 레코드 `+0x2DC`의 특수값도 검사하므로 마을의 모든 다른 플레이어를 같은 규칙으로 단정하지 않는다.

Unity 구현 상태: `ClassArtworkConverter`에 색상 모드 0/2/3의 지정 영역 변환과 별도 PNG·카탈로그 생성 메뉴를 추가했고, `ClassArtworkCatalog.TryApplyRelation`은 명시적인 같은 팀·동맹 판정으로 카탈로그를 선택한다. 기존 기본 카탈로그의 API는 유지하며, 관계 색상 자산이 없으면 다른 색상으로 대체하지 않고 실패를 반환한다. 피부·장비 등 지정 영역 밖의 색상은 유지한다. `ClassRelationColorTests`에 전체 256인덱스 대조와 누락 관계 자산 검사를 작성했다. 다만 Unity MCP 응답 지연으로 컴파일·자산 생성·테스트 실행은 확인하지 못했으며, 실제 유닛 관계 변경 호출 연결과 인게임 색상 검증은 미완료다. 이번 원본 근거는 기계어와 BMP 팔레트의 정적 대조이며 실제 원본 멀티플레이 재현 검증과는 구분한다.

튜토리얼에는 입력 제한·행동 시연·창 안내·대기 명령이 포함된 원본 대본이 있다. 대본의 표시값과 일반 전투 비용을 동일하게 취급하지 않는다. SHOWDIALOG/HIDEDIALOG의 확인된 공통 토글 경로처럼 이름의 사전적 의미와 실제 코드 동작이 다를 수 있다.

수련장 맵/전투 리소스 존재와 원작 몬스터 편성·재생성 주기·자동 종료·사망 후 회복 정책은 별개다. 임의 훈련 몬스터나 무한 리스폰 설정을 원본 배치로 옮겨 적지 않는다.

유령 그림898r.bmp는 확보했다. 그러나 ‘수련장 제외 전투 사망 후 필드 복귀 시 유령’은 사용자 확정 규칙이며 원작 코드에서 전환 조건 전체가 독립 확인된 것은 아니다. 신전 부활 비용·회복량·패킷 승인 경로는 미확정이다. 유령 그림 존재만으로 부활 규칙을 확정하지 않는다.

### 시나리오·연출·보상

시나리오는 맵·설정·연출·등장/이동 명령·이벤트 조건·보상 명령을 연결해서 보아야 한다. 맵 하나=시나리오 하나,아카이브 하나=일반 플레이 시나리오 하나로 가정하지 않는다.

DEE 등의 CHARPOS/LOADSCENE/SETPOSITION 출현은 특정 시점의 등장·위치 근거다. 시나리오 시작 시 전체 몬스터 편성표와 같지 않다. 서버에서 전달될 초기 목록이 누락된 경우 연출에 등장하는 몬스터만으로 빈칸을 채우지 않는다.

원본 지급 명령은 클리어·상자·조건부 이벤트를 구분한다. 최초 클리어 보상으로 명명하려면 완료 조건에서 해당 지급 명령까지 도달하는 경로가 필요하다. 반복 지급 방지·캐릭터 소유 조건·이전 캐릭터 여부는 별도 증거가 필요하다. 기억에 따른 보상표를 이 문서의 확정 목록으로 복사하지 않는다.

근거: [후기 시나리오](../분석/Saver_Late/scenarios.json), [클리어 연결 분석](../분석/Saver_Late/clear_rewards.json), [지급 명령](../분석/Saver_Late/reward_commands.json), [배치 명령](../분석/Saver_Late/placement_commands.json).

### 화면·음향·시간

바닥·장식·유닛·효과·UI의 표시 순서는 그림 종류뿐 아니라 맵 객체와 깊이 계산에 따라 판단한다. 나무 전체를 캐릭터 앞 또는 뒤에 일괄 배치하는 규칙을 원작으로 가정하지 않는다. 스프라이트 투명색·피벗·셀 중심·텍스처 확대 방식도 별도 검증 대상이다.

원본 그림과 LSC의 배치 일치가 글꼴·창 이동·커서·호버·시간까지 일치한다는 의미는 아니다. 실제 렌더 결과와 입력 판정을 따로 확인한다. 음원 파일명/재생 상태는 실제 청음 일치의 증거가 아니다. 시나리오1의 기억 속 음악은 확정 음원 매핑으로 사용하지 않는다.

### 통신과 상태 소유권

요청 생성→직렬화→수신 파싱→화면/상태 소비의 증거를 연결한다. opcode만 같아도 요청·응답 방향과 길이가 다를 수 있다. 레코드ID·직업ID·그림ID·슬롯인덱스를 구분한다.

패킷 필드의 구조가 확인돼도 필드의 게임 의미가 미확정일 수 있다. 서버 내부 승인·권한·보상 공식은 클라이언트 문자열만으로 복원하지 않는다. 전체 로그인/맵 초기화 송신 순서는 부분적인 호출 순서와 구분한다. 로컬 구현을 위해 만든 Notify_* 이름은 원작 wire 규격의 근거가 아니다.

## 서버 패킷 제외 클라이언트 재대조 (2026-10-30)

이번 절은 후기 원본 파일을 다시 읽은 결과다. Unity 코드 동작을 원작 근거로 사용하지 않았으며 게임 코드·씬·저장을 수정하지 않았다. 아래 집계는 명시한 자료의 전수 대조이지 전체 클라이언트 기능 완료율이 아니다.

### 테이블 참조의 확정 및 오류 구분

- magictbl 단독 대조에서 누락으로 보였던 26개 ID 중 **14개는 solskill의 6/7단 고용 기술**이다. 원문 이름·병종 목록·고용 수·행 번호를 기록했다. 관련 성장표 참조는651곳이다. “26개 모두 정의 불명”으로 읽으면 안 된다.
- **107~118의12종**은 magictbl/solskill 어디에도 없다. 성장 키386:1~398:1 중 해당 행들과734:1~744:1 중 해당 행들, 총24곳을 JSON에 열거했다. 임의로107→101 등의 보정은 하지 않는다.
- `magicptn`의64/65 부재와 `magictbl`의6601~6603→64,8101~8103→65 참조를 재확인했다. 표 간 참조 불일치는 확정이며, 실제 소비 코드의 별도 처리 여부는 미확정이다.
- 성장표17열45행은 직업301~315의 레벨1~3에 한정된다. 163:35의1381/1382행은 토큰 전체가 같고, 빈 목록 토큰70개는 직업166에 한정된다.
- 복원 실패2개는 `gameres/set.arc`의`ability_bak.at`, `levelabl_bak.a`에서 발생한 EOF다. 확인한 GameCtl/UserUnit/setunit/DManage4개 DLL에는 해당 파일명 리터럴이 없다. 이것만으로 파일이 절대 사용되지 않는다고 단정하지 않는다.

### 튜토리얼의 전체 원문 순서와 실제 명령 분기

- 초기/후기 원문은 줄바꿈을 정규화한443행이 같다. 유효 명령420개, 대사100개, 명령 이름44종을 **원문 행·실행 순번·인자 그대로** [JSON](../분석/Saver_Late/tutorial_command_sequence.json)과 [CSV](../분석/Saver_Late/tutorial_command_sequence.csv)에 기록했다.
- 시작 원문은 맵301→`bgm\nco01.mid`→시점(10,7)→튜토리얼 입력 제한이다. 초기 배치는 COM0/유닛000(2,6), 직업125/유닛100(18,6), 직업301/유닛400(7,6)·410(13,6)이다. 원문의 배치와 실제 생성/능력치 소비는 구분한다.
- 마지막 원문은 직업805/유닛800(18,11) 등장, (18,7) 이동, `WAITFORMOVEEND 800`, 안내 대사와 대기 후 `ENDGAME`, `END`다. “원문에 대기 명령이 있으므로 실제로 대기했다”는 결론은 아래 디스패치 확인과 구분한다.
- 아이콘 설명은 `CHARMENU 999 <마스크>`→`DO 500`→마스크0→`DO 500`→원래 마스크→`DO 500`이다. 활성/비활성 강조가 원문에 존재한다. Unity에서 한 프레임 회색 전환을 제거한 요청을 원문 자체의 동작으로 재인용하지 않는다.
- 후기 `GameCtl.dll` SHA256 `f8aca791efc019ac44610077e46521a68223afa8ee5c894dcee4083be0116da0`의해석기`0x10010F20`을대조했다.44개명령이름중39개는문자열비교분기에등장한다. 이것은39개전체의효과/타이밍검증완료가아니다.
- **CHARDIR, CHARSETSKILL, SETHP, SETMP, WAITFORMOVEEND**의5개표기는이해석기의전용비교분기에없다. 첫공백앞토큰추출은`0x1000F110`, 명령인덱스선증가는`0x100112E8..100112F0`, 문자열끝까지비교는`0x10011303..1001132C`다. 마지막비교불일치`0x10013AA6`는정리경로`0x10013CEA`로이동해1을반환한다. 이경로에서는원문이름만으로방향/특수기설정이나대기를주장할수없다. 다른실행기로일반화하지않는다.
- 특히 `SETHP/SETMP`를`HPSET/MPSET`과, `WAITFORMOVEEND`를`WAITMOVEEND`와같은명령이라고대입하지않는다. 기존Unity실행기가이별칭을지원하는것은원작동작확정근거가아니다. 이번작업은분석만수행했고실행기를바꾸지않았다.

#### 누락 패턴64·65의 클라이언트 처리

마법6601~6603/8101~8103은 각각 패턴64/65를 참조하지만 후기 `magicptn.atr`에는 해당 행이 없다. `setunit` 로더는 **읽은 ID×328** 위치에만 레코드를 채운다(`10002063..100021F8`). 패턴 배열 `10021BB0`에서 64·65 레코드는 PE의 파일에 없는 zero-fill 가상 데이터 영역에 있다. 초기 적재 상태는 0이다. `GetPatternTable:10002EC0`은 인덱스로 주소를 계산하며 존재 여부를 판정해 다른 번호로 바꾸지 않는다.

#### 화면 주기와 다른 타이머의 분리

**10ms 타이머의 용도를 확인했다.** `4180F4`에서 등록한 ID1은 MFC 메시지 테이블 `4832D0`의 `WM_TIMER → 4156B0`으로 연결된다. ID1 분기는 문자열 `KEYPRESS`와 비교하고 일치 시 `PostMessage(0x466)`를 보낸다. `483468`의 메시지 테이블은 이를 `415200`으로 연결하며, 여기서 `WM_SYSCOMMAND(0x112), SC_CLOSE(0xF060)`를 보낸다. 이 경로를 게임 화면100fps의 근거로 사용해서는 안 된다.

`GameCtl.Update`의 입력값은 시간이 아니라 **처리 단계 번호**다. 디스패처에서4→`_UpdateCharacter(0)`,5→`_UpdateCharacter(1)`,6→`_UpdateCharacter(2)`를 확인했다. 기본 반환 단계와1/3/7/8/9/100/200의 별도 처리도 JSON에 기록했다. 호스트 `4184B0`에는0~24 순환 단계와 반환0일 때 단계 되돌림 코드가 있다. 이것만으로 단계가25ms마다 또는 초당25번 호출된다고 확정하지 않는다.

`UserUnit`의 그림 선택 보조 함수는 누적 프레임 카운터와 다른 **절대 clock 기반 위상 선택**을 한다.

| 보조 함수 | 식(정상적인 비음수 clock 기준) | 원본 호출 인수 |
|---|---|---|
| `1000AC20` | `(clock()/n)%2` | 100 또는250틱 |
| `1000AC40` | `(clock()/n)%3` | 125틱 |
| `1000AC60` | `(clock()/n)%4`의3을1로 바꿈:0→1→2→1 | 125 또는333틱 |

이 세 함수의 직접 호출12곳을 확인했다. 333틱 왕복 선택은 `1000B768`, `1000BA48`, `1000BBE5`, `1000BC30`; 125틱 왕복은 `1000BDA4`, 125틱3상은 `1000BDC6`이다. 다른100/250틱2상 경로도 JSON에 호출 주소를 기록했다. 렌더링이 늦어지면 이 함수들은 지나간 프레임을 모두 재생하지 않고 현재 clock에 맞는 그림을 고른다. 앞 절의 유형99 효과는 별도 경과 시간 비교 후 카운터 증가이므로 같은 방식으로 통일하면 원본과 달라진다.

`GameCtl:1000E0F4`에는 **실제 `Sleep(500)`** 호출도 있다. F5 키 코드0x74를 처리하고500ms 대기한 뒤 다시 처리하는 특정 경로다. 이를 모든 UI의500ms 지연으로 일반화하지 않는다. 스크립트 `DO500`은 sleep이 아닌 다음 Update에서 clock을 검사하는 대기이므로 같은 구현이 아니다.

4개 모듈의 시간 API IAT 직접 참조99곳을 목록화했다. 함수 포인터를 레지스터에 담는 지점도 포함한다. 이99개는 타이머99개 또는 의미 해석 완료99개가 아니다. 간접 호출 전파, 외부 DLL, 오디오 장치와 표시 장치의 실제 지연은 별도 확인 대상이다.

### 창 검색·복원과 효과음 전환 후속 확인

- 창 검색 보조 함수 `403698 → 475F50`은 관리자 `+18`의 배열을 `+3C`개 순회하며 각 객체의 가상 함수+4 반환 ID를 비교한다. 일치하면 객체 포인터, 없으면0을 반환한다. 창을 새로 생성하는 함수가 아니다. F2의 기존 채팅창 검색 실패가 곧 신규 채팅창 생성으로 이어진다고 해석하면 안 된다.
- `402E46 → 476840`은 위 검색 후 객체가 있을 때만 가상 함수+48을 호출한다. 공통 창의+48은 복원 처리다. 따라서 앞 절의 F2 창 열기 뒤 후속 호출은 위치 설정이 아니라 최소화된 창 복원 요청이다. 없는 창에서는 아무 호출 없이 반환한다.
- `UserUnit:100056A7..100056FC`의 효과 처리에서 분기값0이면 마법 레코드+68 음향 ID가 양수일 때 `soundll.S_PlaySound`를 호출한다. 분기값10에서는 +68 음향을 먼저 `StopSound`하고, +64 음향이 양수이면 재생한다. 두 음향이 모두 항상 동시에 재생되는 구조로 구현하면 안 된다. 이 분기값10을10ms 또는10초로 바꾸는 근거는 없다.
- `GameCtl`과 `UserUnit`의 soundll import 참조 목록을 `분석/Saver_Late/native_audio_call_sites.json`에 저장했다. 호출 지점 목록은 실제 음원 파일 매핑·청음 완료 목록과 다르다. 원시 근거는 `Tools/OriginalClientChecks/evidence/late-window-audio-followup.asm.txt`에 보존했다.

남은 작업은 각 효과 처리의 분기값 생산자, soundll 내부 음원 로드/중복 재생/정지 정책, 다른 창 보조 함수의 의미 대응이다. 원작 재생 실측은 수행하지 않았다.

### 후기 soundll의 효과음 정책 확인

원본 CAB에서 `soundll.dll`을 추출하고 manifest SHA256 `5638332e608b6410d660ab0c9b5cb8b176622235ee09b5bfe9eadfc5bc038163`과 일치함을 확인했다. 근거: `Tools/OriginalClientChecks/evidence/late-soundll-policy.asm.txt`.

- `LoadSound:10002000`은 `gameres\\sound.arc`를 열고 ID0~99의100개 슬롯을 채운다. 파일명은0~9가 `00.wav`~`09.wav`, 나머지는 `10.wav`~`99.wav`. 해당 파일 조회 실패 시 슬롯을0으로 설정한다(`1000212A`).
- `S_PlaySound:10002180`과 `StopSound:100021A0`은 ID로 같은 슬롯 배열 `1000406C`를 조회한다. 슬롯이0이면 반환한다. 이 진입점에는 ID의0~99 범위 검사가 없으므로 임의 ID도 안전하게 무시한다고 해석하지 않는다.
- 재생 본문 `10001DF0`은 객체+8과 전역 음향 허용값 `10004024`가 모두0이 아닐 때만 진행한다. DirectSound 버퍼의 `SetCurrentPosition(0)` 뒤 `Play(0,0,0)`을 호출한다. 같은 ID 요청마다 같은 버퍼의 처음으로 돌아가며, 이 경로에는 새 복제 버퍼 생성·동일음 큐 추가·재생 중 요청 거부가 없다. 재생 flags0으로 반복 옵션도 설정하지 않는다.
- 정지 본문 `10001E20`은 객체+8이 유효하면 동일 버퍼의 `Stop`을 호출한다. 전역 음향 허용값은 검사하지 않는다. 따라서 음향이 꺼진 상태에서도 명시적 정지 요청은 처리된다.
- `SetSound:100021C0`은 전역 허용값을 대입하고 반환한다. 이미 재생 중인100개 버퍼를 순회해서 정지하는 동작은 이 함수에 없다. 새 재생 차단과 현재 재생 중단을 구분해야 한다.

위 내용은 효과음의 DirectSound 경로다. 별도 `CDirectMusic`의 음악 재생·이벤트 처리 정책 및 실제 장치 출력 지연까지 확정한 것은 아니다. 실제 청음·재생 속도 실측은 수행하지 않았다.

### DirectMusic 재생·반복·정지의 원본 분기

근거는 해시 대조한 동일 `soundll.dll`이며 `Tools/OriginalClientChecks/evidence/late-directmusic-policy.asm.txt`에 보존했다. 핵심 인수·조건 바이트를 원본과 검사했다.

- 공개 `CDirectMusic.Play(path,int):10001B10`은 기존 `StopSegment` → `ReleasePort` → `CreateAndAddPort` → `AttemptFileOpen(path)` 순서다. 파일 열기가 실패하면0을 반환한다. 따라서 기존 곡을 유지하면서 새 곡의 로딩 성공을 기다리는 구조로 해석하면 안 된다.
- 파일 열기에 성공하면 **항상 `PlaySegment(1)`**을 호출한다. 공개 Play의 두 번째 int 인수는 이 본문에서 읽지 않는다. 호출자가 전달한 반복 옵션이 그대로 내부로 전달된다고 가정하지 않는다.
- `PlaySegment:10001490`은 필요한 객체 유효성 및 설정 단계의 결과를 검사한다. 반복 인수가0이 아니면 세그먼트 가상 함수+18(`SetRepeats`)에 **1000**을 전달한다(`10001561`). 무한 반복 상수 -1이나 재생 시간1000ms가 아니다. 이후 performance의 `PlaySegment` 호출 flags는 `0x1000`이며 실패 HRESULT이면0을 반환한다. 성공 시 내부 상태+2C를4로 설정한다.

- `ProcessEvent:10001BA0`은 performance 및 세그먼트가 유효할 때 알림1개를 가져온다. 알림 GUID가 원본 상수 `1000312C`와 같고 옵션+48이1이면 공개 Stop을 호출한다. 처리 후 알림 메모리를 반환한다. 이 함수 안에는 알림 큐 전체를 비우는 반복문이나 곡을 다시 여는 호출이 없다. GUID 이름을 대조하기 전까지 이 조건을 모든 음악 종료 이벤트라고 일반화하지 않는다.
