## 관찰과 실행 제약

Entry의 `Stage=Login`은 로그인 화면을 실제 확인했다는 뜻이 아니다. client가 초기화되지 않은 경우의 기본 getter 값도 Login이다. 당시 Canvas가 없었고 화면 UI가 비어 있었다. 이전 실행에서 정상 UI가 있었으므로 이번 관찰은 별도의 실패로 남긴다. 정확한 제품 원인·발생 시점은 근거 부족이며, 도메인 재로딩에 따른 UI 수명주기 문제로 확정하지 않는다.

기존 릴레이 `Unity_RunCommand`는 실행 전에 `EditorReadyHelper.RefreshAndWaitForReady()`를 통해 `AssetDatabase.Refresh()`를 수행한다. 관련 패키지의 해당 메서드와 실제 재컴파일·연결 중단을 확인했다. 대기 중 도메인 재로딩으로 요청 실행 여부가 불명확해질 수 있어, 실제 관찰한 상태를 기준으로 다음 조작을 결정했다. 한 번은 Play=false·컴파일 완료를 확인해 이전 시작 요청이 실행되지 않았음을 구분했다. 이번 시도에선 마을 진입 또는 UI 복구를 확인한 성공 화면은 없다.

## 차단된 제안과 필요한 승인

검토할 수 있는 도구 사본은 `GameViewInputDriver.cs.txt`다. 게임의 서비스 API를 호출하거나 플래그를 설정하는 대신 [Unity 공식 QueueGameViewInputEvent](https://docs.unity.com/en-us/engine/6000.5/script-reference/unityeditor/editorguiutility/queuegameviewinputevent)로 Game View에 마우스·키 이벤트를 전달하는 방식이다. 별도 Editor에만 임시 DisableDomainReload 옵션을 적용하고 종료 시 복원하도록 준비했다. 이는 OS 물리 입력 시험과 구분해야 한다.

**준비한 도구는 실행되지 않았다.** 자동 승인 검토의 거부 이유는 다음과 같다.

> Unity Editor의 QueueGameViewInputEvent로 물리 입력을 대체해 튜토리얼 진행을 유발할 수 있고, 기존 사용자 지침에서 튜토리얼 입력 API·자동 진행 우회가 거부된 범위와 실질적으로 겹친다.

거부 이후 다른 경로나 간접 실행으로 우회하지 않았다. 도구가 제안한 Editor 옵션 변경과 입력 전달도 실행되지 않았다. 사용자의 명시적인 모의 입력 진행 승인, 또는 사용자가 검증 프로필의 튜토리얼을 정상 완료한 뒤 마을에 진입하는 조작이 필요하다. 승인 질문을 채팅에 남겼으며 응답을 기다린다.
