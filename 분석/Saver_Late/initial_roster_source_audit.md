# 시나리오 01~25 초기 몬스터 배치 출처 재확인

2026-10-31. 편집툴의 ‘원본 초기 전투 편성 미확보’가 원작에도 배치가 없었다는 뜻인지, 다른 파일·명령으로 복구할 수 있는지 재조사했다. 게임 리소스·편집 배치·계정은 변경하지 않았다.

## 결론

**원작에 데이터가 없었다고 판단하지 않는다. 확보한 설치 자료에서는 01~25의 완전한 초기 병종·좌표 표를 복구하지 못했다.** 파일명 검색에 그치지 않고 원본 ARC 내부 목록, 백업 멤버, MRC 전체 구조와 후기 실행 코드의 생성 경로를 확인했다.

‘서버가 보냈다’는 말의 코드 근거는 **수신 메시지의 개체·병종·좌표를 실제 캐릭터 데이터에 적용하는 기능**이다. 단순히 SET/POS가 없다는 이유로 내린 결론이 아니다. 이 기능의 존재와 **당시 서버가 01~25에 보낸 실제 전체 배치값**의 확보는 구별한다. 후자의 메시지 기록이나 서버 배치 원본을 확보한 것은 아니다.

## 실제 코드로 확인한 생성 경로

후기 `Saver.exe` SHA256 `dd512172256cf4795717aed156746fe6588b3434ed1e249ae59146e63d6e4689`, `GameCtl.dll` `f8aca791efc019ac44610077e46521a68223afa8ee5c894dcee4083be0116da0`, `UserUnit.dll` `74b2e0489b1025b03fceb5ad74163d1f07c139d394abe1ee2554b26ba837559b` 기준이다. 예전 DLL 주소를 후기 버전에 그대로 적용하지 않았다.

1. 대본 생성: GameCtl `0x1001078F` → `UserUnit.dmSetChar` → `0x1000ED5D`의 구조체 구성 → `0x1000ED67`의 `resetcharacter` 호출. 대본의 CHARPOS 계열 생성 경로다.
2. 메시지 생성: Saver `0x441B0A` → GameCtl의 내보낸 `OnPacketReceive(0x10002D30)` → `0x1000EB10` 디스패처. `5C 50`은 `0x1000C7D0`, `5C 51`은 `0x1000CB90`에서 읽고 각각 `0x1000CAC9/0x1000D045`에서 `resetcharacter`를 호출한다.
3. 실제 데이터 반영: UserUnit `resetcharacter(0x1000B0A0)`는 구조체의 개체 번호를 개체 배열 인덱스로 사용하고, 병종을 캐릭터 `+0x18`, 좌표를 `+0x70/+0x74`에 쓴다. 메시지에서 받은 좌표를 AI AREA로 다시 계산하는 단계는 이 복사 경로에 없다.

GameCtl에 전달되는 메시지의 첫 `5C` 바이트를 오프셋 0으로 센 위치다. 외부 소켓 프레임 헤더를 포함한 오프셋이 아니다.

| 메시지 | 개체 번호 i16 | 병종 i16 | X i16 | Y i16 |
| --- | --- | --- | --- | --- |
| `5C 50` | +2 | +6 | +30 | +32 |
| `5C 51` | +2 | +6 | +42 | +44 |

원본 x86 코드에 **시험용** 메시지 6건(각 메시지 3건)을 입력했다. 예를 들어 `unit=400, job=401, x=14, y=28`을 넣으면 수신 파서가 만드는 구조체와 UserUnit의 실제 캐릭터 필드가 모두 그 값이 된다. 다른 병종·좌표 2조합도 그대로 반영됐다. **이 수치는 실험 입력이며 시나리오01의 실제 초기 배치라고 기록하거나 적용하지 않는다.** CString·메모리 할당·기존 이동 경로 해제는 모델로 대체했고, 원본 애플리케이션·서버 접속·Unity Play를 실행한 결과는 아니다.

## 01번에서 확인되는 내용의 범위

- `01.ai`는 400,410,…,490,700의 AI 참조 11개를 갖는다. 이것이 전체 몬스터 11마리라는 뜻은 아니며, 각 부하의 병종/초기 좌표는 포함하지 않는다.
- `01.deo`는 15개, `01.dee`는 8개로 합계 23개의 CHARPOS 생성문을 가진다. 도입 초반의 400·401을 제거한 뒤 같은 번호로 다른 병종을 생성하므로 한 장의 초기 전투 편성으로 합칠 수 없다.
- `01.evt`의 위치 조건은 32행이다. 상자·이벤트 발동 위치를 초기 몬스터 위치로 바꾸지 않는다.
- `01.srf`는 브르고스궁 소개와 키스라 처치 조건을 담지만 전체 초기 병종·좌표 표는 아니다.

따라서 편집툴의 01~25 ‘미확보’ 상태는 유지한다. 기존 16맵 610개 SET/POS 참조는 별도로 유효하며, 이번 조사로 임의 편성·대형·서버 스폰을 새로 생성하지 않는다.

## 26번 파일의 같은 위치 재확인

원본 복사본 `Assets/_Original/SourceData/Native/map`의987파일(Unity `.meta` 제외)을 검사했다. 26번과 같은 접두 이름은 `26.mrc`, `26t.mrc`, `26bg.bmp`, `26hmap.bmp`, `26set.arc`의5개이며26.mrc와26t.mrc는 바이트가 같다. 원본 이름 뒤의 `.bytes`는 Unity 보존용 확장자다. 별도2600번 맵은26번의 다른 배치 파일로 합치지 않는다.

`26set.arc` SHA256은 `1a2604bc2e22a9a0ecf476e6b57776d24803cd4197cda807676cd92641ed7a4b`이고 내부 파일은 `26.ai`, `26.evt`, `26.set`, `26.pos`, `26.srf`의5개다. 헤더221바이트와 선언된 압축 데이터1402바이트가 전체1623바이트를 정확히 차지한다. 같은 폴더의 ARC113개 모두 헤더/파일 데이터 범위 사이·끝에 미참조 바이트가 없고 범위 중첩도 없다. 따라서 이번 범위에서 파일 목록 밖에 남은 압축 덩어리를 발견하지 못했다. 선언된 파일 내용의 의미가 모두 확정됐다는 뜻은 아니다.

이전 설치본 MAP 폴더의 특이 확장자 파일은 `MapCheckSum.exe`, `CheckSumLog.txt`, `2044t.mrtc`다. 로그는 `맵번호=숫자` 형식이며 EXE 문자열에 MRC 선택 필터와 로그 파일명이 있다. 몬스터 병종/좌표 표라고 판정하지 않았다. 현재 JSON `mapDirectoryReview`에 파일 이름·크기·해시·ARC 멤버/바이트 범위를 남겼다. 이번에는 디렉터리 검사만 실행했으며 이전 원본 코드 에뮬레이션 결과를 재실행으로 보고하지 않는다.

### 전체 설치파일의 맵·배치표 교차 확인

`--installer-maps-only`로 제공된 설치 컨테이너16파일의 크기/SHA256을 현재 원본과 재대조했다. 기존 추출 목록에 연결된 고유 MAP ARC114종은 현재 보존된 해시 일치 복사본에서 헤더와SET/POS를 다시 읽었다. 임시 설치본 전체를 새로 추출하거나 설치/게임을 실행한 결과는 아니다.

| 설치 내용 묶음 | MRC 파일 | 맵 설정 SET.ARC | 비어 있지 않은 몬스터 편성 |

각 전체 설치 내용의 비어 있지 않은 편성은 동일하게26,51~55,314~323이다.324~326은SET/POS 파일은 있으나몬스터SET이 비어 있어 몬스터를 만들지 않는다.01~25의SET/POS는 어느 전체 설치 내용에서도 추가로 확인되지 않았다. MRC 수에는 t변형/실내가 포함되므로 고유 시나리오 수로 해석하지 않는다. EGG3권은 하나의 논리 설치 내용으로 합치며 각 권에 맵 전체가 개별 포함된다는 뜻은 아니다.

부분 패치5개(cspatch,patch0224,patch0702,pch1017,pch1223)는 MRC가 각각1,0,0,5,6파일이며 맵 설정ARC는 없다. 패치의 부분 목록을 전체 설치본의 맵 부재로 해석하지 않는다. 생성기 검사는324의POS 중복 슬롯도 기록하며,SET에 없는중복 좌표를 몬스터로 채우지 않는다. 결과는 JSON `installerMapReview`다.
